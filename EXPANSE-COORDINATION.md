## November 18 audit and work assignments

Owner direction recorded November 18, 2026. Canonical technical handoff: [asset delivery audit and contract](docs/ASSET-DELIVERY.md). Measured evidence: [baseline JSON](docs/measurements/asset-delivery-baseline-20261118.json).

Online MMO/MUD players join one authoritative world hosted by a player's local computer or Render. Device-side presentation assets can reduce repeated downloads; the host selects their versions and remains authoritative for simulation, accounts, permissions and persistence. Clients should ultimately fetch only missing/changed verified resources. This is a planned capability: current browser media caching is page-memory-only, desktop Qt caching is disabled, and no host-versioned persistent asset protocol has been implemented.

**November 18 staging update:** a separate `server/shared_staging.py` entry point now wires the shared engine to authenticated test sessions, live role checks and account-owned characters in a dedicated local world/data directory. It is opt-in and binds only to `127.0.0.1`; public Render MMO routing remains disabled. Local Admin DM access is guarded; Full_Edit cannot moderate, and Creator/live-world editing and publication remain closed pending their own integration. This is a local implementation milestone, not a claim that all gate tests or production validation passed. Follow [the local trial and remaining rollout steps](docs/SHARED-HOST-ROLLOUT.md).

**Latest owner save policy:** MMO automatically saves on exit/disconnect, session revocation or idle timeout; Single Player remains manual **Save / Save & quit**. The isolated staging runtime implements this shared-mode policy without changing existing production account/single-player stores. Record the applicable runtime and save policy in each test report. Earlier asset-audit references to manual saving must not be interpreted as overriding this later MMO-specific direction.

Local staging evidence: [test results and candidate/fixture hashes](docs/measurements/shared-host-staging-20261118.json), including Python 3.12/3.14, real four-client connections, exit/timeout recovery and unchanged private-account isolation. The report lists the production gateway, Creator, full-world trade/gameplay, device, backup/restore and capacity work still required; this is not production acceptance.

The asset audit's recorded server baseline is `bbbe023` (the merged interface-quest fix after the 1.9.17 parity update); it is not a claim that later staging code is already deployed. Desktop package 1.9.17.1 identifies that shared commit and bundles Wild Lands 1.9.15. The separate festival 1.9.18/Wild Lands 1.9.16 handoff is staged and has its own compatibility/deployment prerequisites; inspecting its asset hashes is not authorization to import or deploy it.

Sequence: baseline and real usage → hashed app files/compression → scoped world manifest/binary blobs → bounded browser/native reuse → measured production comparison. Prefer the existing host and client storage before paying for another delivery service. Cache clearing, eviction, update, rollback and account switching must preserve user data. Caching must neither trigger gameplay checkpoints nor change the chosen save policy: MMO exit/timeout saving and Single Player manual saving are runtime responsibilities.

Each workstream should cite the same protocol revision, tested source commit, asset-manifest revision and evidence in its PR/release notes. Record unresolved compatibility questions against this handoff before changing a shared file.
